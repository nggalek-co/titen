# Titen SaaS with prepaid transcription credits

Status: Proposed implementation specification.
Date: 21 October 2026.
Predecessor: [PRD 001](001.md).

## 1. Product goal

Turn Titen into a managed meeting transcription service. Users install the desktop app, sign in, top up their balance, connect Google, and record. Users never create a Soniox account, configure a Google Cloud project, or enter provider credentials.

The product has a native desktop recorder, a web dashboard, and a SaaS backend. Desktop capture remains native. The backend owns paid transcription access, account balances, provider credentials, and Google Docs synchronization.

### Primary success criterion

A new user can sign up, complete a top-up, connect their Google account, and transcribe a meeting into Google Docs without configuring developer credentials. Charges match the published rate and authorized usage. Repeated payment notifications, reconnects, and process restarts do not duplicate charges or transcript text.

### Scope relative to PRD 001

This PRD supersedes the bring-your-own-credentials model and the restriction against a separate backend. It preserves native macOS audio capture, the microphone test, native recording controls, local transcript recovery, and the reliability requirements of PRD 001.

This document specifies new work. Existing local builds and mock tests do not establish SaaS readiness or live provider acceptance.

## 2. Product boundaries

| Component | Owns |
| --- | --- |
| Desktop app | Native microphone and system capture, microphone selection and test, meters, start/pause/resume/stop, partial transcript display, local SQLite recovery, account session, and balance display. |
| Web dashboard | Sign-up and sign-in, top-ups, available and reserved credit, transaction history, meeting history, transcripts, Google connection, and account settings. |
| SaaS backend | Identity and device sessions, account authorization, payment verification, credit ledger, session reservations, transcription proxy, usage accounting, canonical cloud transcripts, and Google Docs jobs. |

Separate the desktop and web interfaces. They use the same backend account and meeting model. The desktop retains its native MyGo UI and Swift capture helper. A web recorder is outside the first release.

Use one backend application with API routes, authenticated WebSocket streaming, and background workers for the initial release. Separate deployment components where runtime needs differ. Microservices and separate repositories are not requirements.

## 3. User journeys

### First use

1. The user creates an account through the web dashboard or the desktop sign-in flow.
2. The user completes a top-up through hosted payment checkout.
3. The backend verifies payment and updates the available balance.
4. The user selects Connect Google and authorizes Titen to create and update documents.
5. The user installs or opens the desktop app and signs into the same account.
6. The user tests their microphone, grants native capture permissions, and starts a meeting.
7. Finalized text appears in the desktop app, meeting history, and the associated Google Doc.

Connecting Google is optional for transcription. A user can record and read transcripts with Google disconnected, then connect it and request document sync later.

### Returning user

The desktop restores its account session from secure storage, displays the current balance, and lists recent meetings. Recording requires an online authorization and sufficient available credit. Reading completed local transcripts and running the microphone test require no paid session.

### Insufficient balance

Before recording, the backend rejects sessions that cannot obtain the minimum credit reservation. The desktop explains the required balance and opens the top-up page.

During recording, the desktop shows a low-balance warning. If the backend cannot extend the authorized reservation, it stops accepting billable audio, finalizes the authorized portion, and instructs the desktop to stop capture. The user retains finalized text and can top up before starting another paid session.

## 4. Identity and account access

Implement one account identity across the web dashboard and desktop app.

- Desktop sign-in opens the system browser.
- Complete desktop sign-in through a standard authorization flow with PKCE and state, or an equivalently protected device authorization flow.
- Browser completion exchanges a short-lived, single-use code for a desktop session. Never place reusable access or refresh tokens in callback URLs.
- Store desktop session credentials in the OS credential store.
- Support sign-out and server-side device-session revocation.
- Authorize every meeting, transcript, document operation, payment, reservation, and ledger query against the authenticated account.
- Separate product sign-in from permission to access Google Docs, even when Google is also an identity provider.

The initial release has individual accounts. Team workspaces and shared balances are outside scope. Concurrent desktop sessions must still share one transactionally enforced account balance.

## 5. Managed provider integrations

### Soniox

Titen operates and pays for the Soniox account. Long-lived provider credentials exist only in backend secret storage.

For the first paid release, audio follows this path.

```text
Native desktop capture
    -> authenticated Titen WebSocket
    -> backend authorization and usage accounting
    -> Soniox WebSocket
    -> backend finalized transcript persistence
    -> desktop updates and Google Docs jobs
```

The proxy validates supported formats, message sizes, audio rate, session ownership, reservation status, and concurrency limits. It enforces backpressure and disconnect deadlines. It must not allow a client to upload audio faster than its authorized budget permits.

Desktop clocks, reported duration, and client balance values are not billing authorities. Bind every provider connection to a server-created transcription session and an immutable usage reference.

Direct desktop-to-Soniox streaming is a future optimization. It requires server-issued temporary credentials, single-use restrictions, maximum session duration, credit reservations, and reliable provider-usage reconciliation. A short credential lifetime alone does not terminate an existing stream. Do not ship that optimization until its spending limits and reconnect behavior are proven.

### Google Docs

Titen registers and operates the Google OAuth application. Users click Connect Google and grant access. They never enter an OAuth client ID or client secret.

- Handle the Google authorization callback and token exchange on the backend.
- Request the minimum necessary scope for the supported document flow.
- Encrypt Google refresh tokens at rest with keys managed separately from application data.
- Keep Google tokens out of desktop clients, logs, and browser storage.
- Create one document per meeting by default.
- Preserve transactional transcript persistence, durable jobs, batching, retry backoff, and ambiguous-append reconciliation.
- Continue document synchronization after the desktop app closes.
- Allow disconnect and reconnection. Revoked access must produce an actionable sync state without stopping transcription.

App-created documents are the initial supported destination. Selecting an unrelated existing document requires an explicit per-file authorization mechanism such as Google Picker. A pasted document ID is not sufficient authorization. Validate access before committing a destination.

The append deduplication mechanism does not make document creation idempotent. Handle ambiguous create results separately and document any remaining orphan-document behavior before release.

## 6. Prepaid top-ups and credit accounting

### Customer-facing behavior

Users buy credit through the web dashboard. Both interfaces show available credit, reserved credit, the applicable transcription rate, and usage history. Show an estimated remaining recording duration with its rate assumptions.

Publish the currency, top-up denominations, minimum charge, rounding, expiration policy, and refund policy before payment. Final commercial values remain launch decisions. Do not hardcode invented prices or silently expire balances.

### Ledger model

Use an append-only transactional ledger. Store money or credit quantities as integer units. Never use floating-point arithmetic for balances or charges.

Support these economic events.

| Event | Meaning |
| --- | --- |
| Top-up | A verified successful payment adds purchased credit. |
| Reservation | Credit becomes unavailable to other sessions while remaining unspent. |
| Usage settlement | Authorized transcription usage consumes reserved credit. |
| Reservation release | Unused reserved credit becomes available again. |
| Refund or adjustment | A separate auditable entry changes the balance and references its cause. |

Derive balances from authoritative entries. Cached balances must be reconcilable. Every payment credit, usage settlement, and adjustment has a unique idempotency key.

### Session spending

1. Atomically reserve an initial budget before opening a provider stream.
2. Extend the reservation in bounded increments while credit remains available.
3. Record server-observed accepted audio intervals with unique sequence identifiers.
4. Settle actual authorized usage against the rate version captured when the session starts.
5. Release unused credit after outstanding usage is settled or reconciled.

Define a configurable maximum unsettled exposure and reservation increment before implementation. The sum of active reservations cannot exceed available account credit. Concurrent sessions cannot spend the same credit.

For the initial product, bill accepted audio duration, including silence, at a published time-based rate. Paused capture and the local microphone test are free. Define rounding once per meeting, rather than repeatedly rounding reconnect fragments.

A reconnect continues the same logical meeting and usage accounting. Replayed audio chunks cannot charge the customer twice. Provider duplicate processing costs caused by Titen recovery do not automatically become a second customer charge.

A client disconnect is not evidence that provider costs have stopped. Close or bound the upstream stream, reconcile uncertain usage, and then release credit. Expired reservations cannot be released while a corresponding provider session can still spend them.

### Payment verification

- Use provider-hosted checkout for the first release.
- Create checkout orders on the backend with fixed account, amount, currency, and external references.
- Verify webhook authenticity and match the confirmed payment to the stored order.
- Credit the ledger only after authoritative payment confirmation.
- Treat checkout redirects as display events, not proof of payment.
- Handle duplicate and out-of-order webhooks without duplicate credit.
- Reconcile missing webhooks against provider records.
- Represent refunds and chargebacks with separate ledger entries and an explicit account policy.

The payment provider is not selected in this PRD. Real payment activation is a separate launch step.

## 7. Transcription and meeting persistence

Preserve Indonesian and English transcription, partial updates, finalized segments, timestamps, and speaker labels where available.

The backend is the authority for cloud meeting state and finalized transcripts. Persist each finalized segment and its Google synchronization job transactionally before acknowledging durable delivery to the desktop.

The desktop stores acknowledged finalized text in local SQLite for offline access. Local pending text recovery uses stable meeting and segment identities. Reconciliation after reconnect cannot duplicate cloud transcript segments or Google text.

Keep these states separate.

| State machine | Example states |
| --- | --- |
| Recording | Idle, starting, recording, paused, stopping, stopped, failed. |
| Transcription session | Authorizing, active, reconnecting, finalizing, closed, failed. |
| Credit reservation | Active, reconciling, settled, released. |
| Google synchronization | Disconnected, pending, syncing, synced, retrying, action required. |
| Payment | Pending, confirmed, failed, refunded, disputed. |

Audio buffers must have explicit memory, disk, and retention limits. Explain any lost unfinalized speech. Do not present missing speech as a complete transcript.

An online connection is required for new paid transcription. Completed local transcripts remain readable offline. A network outage does not authorize unlimited offline recording or an unbounded later upload. Any buffered recovery must fit the existing session authorization and spending limits.

## 8. Required interfaces

### Desktop

- Sign in, sign out, and account identity.
- Available balance, estimated remaining duration, low-balance status, and Top up link.
- Existing native recording controls, device settings, source modes, duration, and independent meters.
- Local microphone test without provider access or billing.
- Live and finalized transcript view.
- Connection, recovery, finalization, and Google synchronization status.
- Local meeting history, copy transcript, and links to the web meeting and Google Doc.
- Visible recording and microphone-test indicators while the main window is hidden.

Remove provider-key and Google developer-credential fields from the customer interface. Keep capture settings native.

### Web dashboard

- Authentication and onboarding.
- Available and reserved balances.
- Top-up checkout and payment result states.
- Ledger history, usage history, and payment references.
- Searchable meeting history and meeting details.
- Transcript copy or export and associated Google Doc link.
- Google connection and synchronization recovery.
- Desktop download and sign-in entry points.

The web dashboard does not need native capture controls or browser-based system-audio recording in the initial release.

### Operations

Provide restricted operational access to payment reconciliation, stuck reservations, unsettled sessions, failed synchronization, provider usage, and audited ledger adjustments. Do not expose provider secrets through an administrative interface.

## 9. Security, privacy, and reliability

- Encrypt traffic between the desktop, backend, and providers.
- Enforce account isolation in database queries, stream authorization, jobs, and exports.
- Keep provider secrets in backend secret storage and desktop account tokens in Keychain.
- Bind payment events and transcript jobs to immutable account and operation identities.
- Redact credentials, raw audio, and transcript text from routine logs.
- Log structured session, payment, reservation, settlement, and retry events with correlation IDs.
- Retain raw audio only for bounded operational recovery unless the user explicitly opts into a recording feature.
- Publish transcript retention and deletion behavior. Deletion must account for cloud data, device copies, pending jobs, and independently owned Google Docs.
- Preserve accounting records according to the adopted retention policy without retaining transcript content unnecessarily.
- Apply per-account and per-device concurrency and rate limits.
- Keep capture independent of slow cloud writes and payment processing.
- Bound upstream provider sessions after lost clients, worker crashes, or backend restarts.
- Keep completed transcripts accessible when credit reaches zero.

## 10. Migration from the current implementation

Reuse the Swift native capture helper, source-tagged PCM protocol, Go audio processing, native MyGo views, microphone test, and local SQLite transcript history.

Replace desktop-owned Soniox access with an authenticated Titen streaming client. Move Google OAuth tokens, document creation, and document synchronization into backend services. Add cloud meeting and segment identifiers to local recovery records.

Preserve existing local transcripts. Do not upload historical transcripts or migrate local provider credentials automatically. Existing local Google connections require a new managed authorization flow when users choose cloud synchronization.

Remove obsolete customer credential configuration after the managed path works. Do not leave a hidden path that bypasses SaaS authorization or billing in release builds.

Use a transactional server database for accounts, payments, ledger entries, reservations, usage intervals, cloud meetings, transcripts, and jobs. PostgreSQL is the proposed default. SQLite remains a device-local store. Revalidate dependencies and deployment requirements during implementation.

## 11. Implementation phases

### Phase 1. Accounts and backend foundation

Implement account identity, desktop browser sign-in, account isolation, server database migrations, and a minimal web dashboard. Preserve native capture behavior.

### Phase 2. Ledger and payments

Implement integer credit accounting, reservations, hosted checkout integration, verified webhooks, and reconciliation. Use provider test mode and explicit non-purchasable development credits until live payments are approved.

### Phase 3. Authorized transcription

Implement the backend streaming proxy, session budgets, server-side metering, rate snapshots, reconnect identities, and settlement. Prove that insufficient or concurrently reserved credit cannot authorize excess usage.

### Phase 4. Managed Google Docs

Implement backend OAuth, encrypted token storage, durable document creation, finalized transcript persistence, and idempotent append jobs. Prove synchronization continues while the desktop is closed.

### Phase 5. Customer experience and migration

Replace credential settings with account and balance controls. Add the complete web history and transaction views. Preserve local history and validate sign-out and recovery behavior.

### Phase 6. Release validation

Run real macOS capture, provider, OAuth, payment test-mode, outage, and long-session acceptance. Complete Google production authorization requirements and distribution signing. Activate live payments only after reconciliation and spending enforcement pass.

## 12. Acceptance tests

Automated tests must prove these behaviors.

- One confirmed payment credits the account once despite duplicate or reordered webhooks.
- A forged webhook or successful browser redirect alone adds no credit.
- Concurrent recording starts cannot reserve the same balance twice.
- Reconnects, duplicate usage events, and finalization retries cannot double-charge.
- A crashed or disconnected client cannot leave an unlimited billable provider stream.
- Reservation recovery does not release funds before uncertain usage is resolved.
- Low balance produces a warning and enforces the authorized audio limit.
- Pause and microphone tests create no billable usage.
- Finalized transcripts survive process restarts and appear once in cloud storage and Google Docs.
- Document sync continues after the desktop closes.
- Revoked Google access does not interrupt transcription or lose pending text.
- An account cannot read another account's meetings, balance, payment, or stream.
- Sign-out revokes device access while preserving the documented offline-history behavior.
- The released desktop bundle contains no long-lived provider credentials.

Live acceptance must include a new user with no developer credentials, payment test mode, Google consent, simultaneous microphone and system audio, headphones, Indonesian and English speech, and a meeting lasting at least 60 minutes. Test network loss, backend restart, lost client connections, and insufficient balance during recording. Record actual results separately from mock and build checks.

## 13. Launch decisions still required

These decisions must be resolved before accepting real customer payments.

- Payment provider, supported currency, top-up amounts, and checkout methods.
- Customer rate, minimum charge, rounding, reservation increments, and maximum unsettled exposure.
- Credit expiration, refunds, chargebacks, and account restrictions.
- Transcript retention, deletion, backups, and deployment region.
- Hosting for persistent WebSockets and background jobs.
- Product sign-in provider, desktop callback mechanism, and Google production OAuth configuration.
- Whether arbitrary existing Google Docs selection belongs in the first release.

## 14. Non-goals for the first release

Team wallets, subscriptions, browser recording, Windows capture, Linux capture, meeting bots, third-party transcription providers, and user-managed provider keys are outside scope.

## 15. Design principles and references

Model the Domain makes accounts, reservations, payments, and transcription sessions distinct records with explicit state transitions. Make Operations Idempotent requires stable identities and reconciliation for external events. These principles shape the requirements above.
