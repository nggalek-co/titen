# Build a Cross-Platform Native Meeting Transcription App

You are a senior desktop systems engineer specializing in Go, macOS native APIs, real-time audio processing, and cross-platform applications.

Build a lightweight, production-oriented native desktop application for recording meetings and lectures, transcribing speech in real time using Soniox, and synchronizing finalized transcripts to Google Docs.

The application must run on macOS first, with an architecture that supports Windows and potentially Linux later.

## 1. Core Technology Stack

- **Desktop framework:** MyGo (https://github.com/egoist/mygo)
- **Primary language:** Go
- **UI:** MyGo native GPU-rendered UI, not WebView by default
- **macOS audio:** Swift + ScreenCaptureKit
- **Windows audio (future):** WASAPI microphone and loopback capture
- **Speech recognition:** Soniox real-time WebSocket API
- **Storage:** SQLite
- **Cloud integration:** Google Docs API + OAuth 2.0 with PKCE
- **Target platforms:** macOS 15+ initially, Windows later, Linux optional

Prefer lightweight binaries, minimal dependencies, low memory consumption, and a responsive native UI.

Do not introduce Electron, a browser runtime, or a separate backend server.

## 2. Mandatory Research and Validation

Before implementing, inspect the latest official documentation and repository sources for:

1. MyGo framework, native widgets, application lifecycle, tray support, global shortcuts, packaging, and build requirements.
2. Apple ScreenCaptureKit, specifically simultaneous microphone and system audio capture.
3. Soniox real-time transcription API, authentication, audio formats, partial/final tokens, speaker diarization, and connection limits.
4. Google Docs API, OAuth scopes, document creation, batch updates, and rate limits.

Do not invent APIs or assume documentation examples are current.

Compare 3–5 implementation approaches where relevant, then select the 1–2 most reliable and efficient options.

Explicitly validate:
- Whether MyGo's native UI supports the required widgets.
- Whether a separate Swift helper process is necessary.
- Whether ScreenCaptureKit can capture microphone and system audio independently.
- Which macOS permissions and entitlements are required.
- Whether Soniox supports the selected streaming audio format.
- Whether the selected Google Docs scopes are sufficient.

Document findings and architectural decisions in `docs/architecture.md`.

If a dependency or API is unavailable, select a practical alternative and explain the trade-off. Do not silently replace MyGo with another desktop framework.

## 3. Application Features

### Recording

Implement:

- Start, pause, resume, and stop recording.
- Simultaneous microphone and system audio capture.
- Select microphone input device.
- Display microphone and system audio levels independently.
- Recording duration indicator.
- Visible recording status.
- System tray/menu bar recording controls.
- Proper permission requests and actionable error messages.

Capture must work when headphones are connected and during Google Meet, Zoom, or Microsoft Teams meetings.

Avoid microphone echo and duplicated audio where possible.

Recording must continue when the main application window is minimized or hidden.

### Real-Time Transcription

Integrate Soniox using its official real-time WebSocket protocol.

Support:

- Live partial transcription.
- Finalized transcription segments.
- Timestamps.
- Speaker diarization where available.
- Automatic reconnection.
- Graceful network failure handling.
- Long-running meeting sessions.
- Indonesian and English speech.

Partial transcription should update immediately in the UI.

Finalized transcription must be persisted locally before cloud synchronization.

Do not duplicate finalized text after reconnecting.

### Google Docs Integration

Implement Google OAuth using the system browser and PKCE.

Support:

- Sign in with Google.
- Create a new Google Doc for each meeting.
- Optionally select an existing document.
- Append finalized transcript segments.
- Batch updates approximately every 3–5 seconds.
- Retry transient failures with exponential backoff.
- Resume synchronization after application restart.
- Show synchronization status.

Use the minimum necessary OAuth scopes.

Never store OAuth refresh tokens in plaintext SQLite. Use the operating system's secure credential store.

Avoid duplicate text when recovering from ambiguous API failures.

Google Docs synchronization must never block audio capture or transcription.

### Local Storage

Use SQLite to store:

- Meeting sessions.
- Recording metadata.
- Finalized transcript segments.
- Speaker information.
- Google document references.
- Synchronization checkpoints.
- Pending synchronization operations.

Use transactions where appropriate.

All completed transcripts must remain accessible offline.

## 4. macOS Audio Capture

Prefer a dedicated Swift helper process using ScreenCaptureKit.

Requirements:

- Capture system audio and microphone audio simultaneously.
- Preserve both as independently identifiable sources.
- Use native macOS capture APIs.
- Avoid virtual audio drivers such as BlackHole unless absolutely necessary.
- Support audio capture with headphones.
- Handle device changes and permission revocation.
- Recover from stream interruptions.
- Shut down capture cleanly.

Use a lightweight binary IPC protocol between Swift and Go, preferably a Unix domain socket with framed messages.

Do not encode PCM audio as JSON or base64.

Audio frames should include:

- Source identifier.
- Timestamp.
- Sample rate.
- Channel count.
- Sample format.
- Audio payload.

Implement backpressure handling with bounded buffers.

Do not let slow consumers accumulate unlimited memory.

Keep the Swift helper narrowly scoped to native audio capture. Business logic belongs in Go.

## 5. Audio Processing

Build a Go audio pipeline that:

1. Receives microphone and system audio frames.
2. Aligns audio using capture timestamps.
3. Converts input to a common internal format.
4. Resamples when necessary.
5. Handles mono/stereo conversion.
6. Mixes streams with appropriate gain management.
7. Encodes audio into the format required by Soniox.
8. Streams audio over WebSocket.

Prevent clipping, unnecessary buffering, and excessive latency.

Design the pipeline to support two transcription modes:

**Mode A: Mixed audio (MVP)**

Combine microphone and system audio into one Soniox stream.

**Mode B: Separate transcription (future)**

Send microphone and system audio to independent Soniox sessions, then merge timestamped transcripts.

Implement Mode A first, but retain source separation internally so Mode B can be added without rewriting capture.

## 8. Reliability Requirements

The application must:

- Continue recording when minimized.
- Survive temporary network outages.
- Persist finalized transcripts before synchronization.
- Handle Soniox connection termination.
- Avoid unbounded memory growth.
- Avoid blocking audio capture on network operations.
- Shut down helper processes cleanly.
- Recover incomplete sync operations after restart.
- Prevent duplicate transcript segments.
- Provide useful structured logs.

Audio capture, transcription, persistence, and Google Docs synchronization must operate independently.

Use context cancellation and bounded channels appropriately.

## 9. Security and Privacy

- Store Soniox credentials securely.
- Store Google OAuth tokens in the OS credential store.
- Never log credentials or raw audio.
- Request only necessary macOS permissions.
- Clearly indicate when recording is active.
- Keep local transcripts private.
- Avoid uploading audio anywhere except the configured transcription provider.
- Do not implement hidden or covert recording.
